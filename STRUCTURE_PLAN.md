# WinWrap structure and naming update

Owner: `Refactor/Winwrap-Structure`, based on `Feature/Device-Io` because `Device` is not yet on `origin/main`. Continue in this existing worktree and draft PR #8. Do not create another worktree. A fresh Codex session is being launched to investigate and fix the reopened mixin layout decision.

## Authorized outcome

Apply Tommy's approved window-subsystem organization and clearer file names. Investigate and fix the inconsistent mixin categorization and naming: `notification::TextChange` is a mixin under `notification/command/`, while other mixins are grouped under `window/mixins/`. Organize by the Win32 behavior or protocol the header represents, with "mixin" treated as a composition mechanism rather than a mandatory folder category. Do not impose `-able` on every mixin; use names that describe each behavior naturally. Keep the descriptive `WindowConfig`, `ControlConfig`, and `NotifyIconConfig` names. Fold the private interface-list parser into the Device component. Preserve runtime behavior and the `winwrap::winwrap` target. Do not touch driver or host machine state.

## Decisions

- Put desktop UI APIs under `winwrap/desktop/`: `window/` for HWND-backed windows and controls, `menu.hpp`, `drop.hpp`, and `notify_icon.hpp` for independent resources, and `message_loop.hpp` for the calling thread's pump. Keep `NotifyIcon` and `NotifyIconConfig` named as they are.
- Group the control `WM_COMMAND` notification protocol under `desktop/window/notification/command/`. Keep one header per public notification mixin, a focused `protocol.hpp` for the shared message and matching helper, and `reflection.hpp` for the parent-side `CommandReflection` mixin. Keep it separate from `WindowCommand`: the latter handles menu and accelerator commands with no child HWND, while reflection returns a child notification to its control. Do not invent a `callbacks.hpp` aggregate.
- Name the router's private call-through `invoke_mixin`; it invokes another object's handler and is not itself a message handler.
- `notify_folder_changed` belongs in `desktop/shell/change_notification.hpp`, named for the Shell change-notification protocol it wraps. `folder.hpp` suggests a broad Folder resource; `changes.hpp` does not identify the protocol. Public headers for owning types use the type name. Free operations without a type owner group by a stable operation family or native protocol, even when the first header has one function. Add deeper folders only for a real family of public headers. Do not invent operations to fill a header.

- Group Window, Control, concrete controls, routing, reflection, and mixins under `winwrap/desktop/window/`.
- Put the message-loop header under `desktop/` because it pumps the calling thread, not one window. Leave its public `run()` and `quit()` names unchanged in this structure change.
- Remove `mixins.hpp` and `controls.hpp` as implementation dependencies. Focused headers must compile independently. No new public alias headers are planned for this experimental v0.1 layout unless consumer evidence requires them.
- `WindowHandle` is a shared non-owning implementation base, not a standalone owned handle. Choose a precise name and home without changing its behavior.
- The interface-list parser belongs in `device.hpp`, as Tommy requested. Remove the separate `device_paths.hpp` while retaining the malformed-list tests. Keep the parser in `detail` unless a type-owned public parsing operation has a real consumer; do not expose a test-only Device method.
- Keep `filesystem/attributes.hpp`; move the Shell operation as described above.
- Keep `Menu`, `NotifyIcon`, and `Drop` outside the window folder as independent desktop resources. Keep `Device`, filesystem attributes, and generic error support outside desktop.
- Group the direct HWND message-routing system under `desktop/window/message/`: `MessageRouter`, the eight `on_*` behavior providers, and the internal `detail/hook_case.hpp`. Keep reflected control notifications under their more specific `desktop/window/notification/command/` protocol. `window/` itself owns the HWND-backed object abstractions, while mixin remains a composition mechanism rather than a directory taxonomy.
- Mirror the single library target with `libs/winwrap/` and `tests/winwrap/`; retain the public target and include root.
- Keep `WW_CASE` as the concise, library-prefixed hook macro. Its shared header lives at `desktop/window/message/detail/hook_case.hpp`: reachable because public templates include it, but unsupported for direct consumer use. `detail/` is an API-support convention, not access control; consumers can physically include the header, but no compatibility is promised. A macro cannot be placed in a C++ `detail` namespace, so the `WW_` prefix supplies collision protection. Each public behavior header must compile independently.
- Name the message fold `MessageRouter` with `route_message`; mixins keep `handle_message`. Use singular behavior names for hook mixins: `Lifecycle`, `SizeChange`, `WindowCommand`, `Paintable`, `MouseInput`, `KeyboardInput`, `FocusAware`, and `FileDroppable`. `-able` is valid for an actual capability; avoid a blanket `*Messages` suffix. The callback mixins remain named for their notifications.
- Callback mixins currently live under `desktop/window/notification/command/` with short names in the `notification` namespace: `Click`, `TextChange`, and `SelectionChange`. They expose callbacks for control notifications; the control itself already supports clicks or text changes without the mixin. Review their placement and names alongside all other mixins rather than assuming this exception is final.
- Use the established Win32 term *message reflection* for a parent returning a control notification to the child. Scope the current implementation to `WM_COMMAND` with `notification::CommandReflection` under `desktop/window/notification/command/`.

## Structure review

- The settled layout uses the public resource or protocol as its boundary, not the Windows DLL called inside. The folder name `shell/` remains for the Shell change-notification protocol; `NotifyIcon` is a desktop resource. A hypothetical `TaskbarProgress` owner would get a focused desktop header. A hypothetical free monitor query would get a display-monitor concept header; window discovery would live under `desktop/window/`; file-attribute operations remain together; open-device operations remain on `Device`; independent device-interface discovery gets its own device concept. Add no such operations without a consumer. Microsoft documents `SHChangeNotify` as a family of Shell events and notification icons as taskbar resources: https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shchangenotify and https://learn.microsoft.com/en-us/windows/win32/shell/notification-area.
- `CommandReflection` and `WindowCommand` remain separate. The former handles child-origin `WM_COMMAND`; the latter handles menu and accelerator `WM_COMMAND`. A future `WM_NOTIFY` protocol remains outside this change.
